# Verify Publish Correctness Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add a `check:exports` phase to `bun run build` that runs `@arethetypeswrong/cli` and `publint` against the packed tarball so a typo'd `exports` path or any other publish-correctness regression fails the build instead of breaking consumers at `npm install` time.

**Architecture:** Two off-the-shelf CLIs added as devDependencies and chained as the third phase of the `build` script (after `build:js` and `build:types`). attw simulates Node module + types resolution against the packed tarball; publint statically validates `package.json` for publishing correctness. Both exit non-zero on failure, so chaining via `&&` makes the whole `bun run build` fail. The hardcoded `Verify build artifacts` step in `.github/workflows/ci.yml` is removed because the new check supersedes it and scales with the `exports` map.

**Tech Stack:** Bun (toolchain, `bun add`, `bun pm pack`, `bun run`), `@arethetypeswrong/cli` (Node CLI invoked via `bunx`), `publint` (Node CLI invoked via `bunx`), GitHub Actions YAML.

**Spec:** [`docs/superpowers/specs/2026-04-16-verify-publish-correctness-design.md`](../specs/2026-04-16-verify-publish-correctness-design.md)

**Issue:** [#32](https://github.com/evans-sam/ad-unit-component/issues/32)

## Task 2: Run baseline check against current `dist/`, capture findings

**Files:** None modified — investigation only.

Build the package, then run both CLIs to see what they report on the current state. The list of findings drives Task 3's triage.

- [ ] **Step 1: Build the package fresh**

Run:

```bash
rm -rf dist
bun run build
```

Expected: `dist/index.{js,d.ts}` and `dist/adapters/{gam,prebid,apstag}.{js,d.ts}` all present. Build exits 0.

- [ ] **Step 2: Run attw with the spec's starting ignore-rules**

Run:

```bash
bunx attw --pack . --ignore-rules cjs-resolves-to-esm
```

Capture the full output. Note any rule names reported and which entrypoints they affect. Example rule names to look out for: `no-resolution`, `untyped-resolution`, `false-cjs`, `false-esm`, `cjs-only-exports-default`, `unexpected-module-syntax`, `internal-resolution-error`.

- [ ] **Step 3: Run publint with the spec's starting flags**

Run:

```bash
bunx publint --strict --pack bun
```

Capture the full output. publint findings have codes (e.g. `EXPORTS_TYPES_INVALID_FORMAT`, `FILE_NOT_FOUND`, `EXPORTS_MODULE_SHOULD_BE_ESM`). Note each one and which path it points at.

- [ ] **Step 4: Categorize each finding (mental triage, no commit)**

For every line of output from steps 2 and 3, place it in one of three buckets:

1. **Real bug** — the package is genuinely wrong; we should fix the package, not suppress the rule. Examples: a path in `exports` resolves nowhere; `files` array doesn't include `dist`.
2. **Expected noise per design** — the rule fires because of a deliberate design choice already documented in the spec. Examples: any further CJS-related rule we deliberately don't support beyond `cjs-resolves-to-esm`.
3. **Needs design discussion** — neither of the above; ambiguous; might need a spec amendment. **STOP and surface this to the user before continuing.**

Carry this categorization forward into Task 3.

## Task 5: Probe gap closure — corrupt an exports path, confirm the build fails

**Files:** None permanently modified — temporary corruption is reverted within this task.

This is the test that this whole effort closes the originally-stated gap: a typo in `exports` should fail the build, not pass.

> **Abort safety:** If anything in this task goes sideways, run `git checkout -- package.json` to restore. The corruption is intentionally local-only; nothing is staged or committed before the revert step.

- [ ] **Step 1: Build cleanly first**

Run:

```bash
rm -rf dist
bun run build
```

Expected: exit 0. (Establishes a known-good baseline.)

- [ ] **Step 2: Temporarily corrupt one enumerated subpath**

Open `package.json`. Change the `import` value of the `./adapters/gam` entry from:

```json
"./adapters/gam": {
  "import": "./dist/adapters/gam.js",
  "types": "./dist/adapters/gam.d.ts"
},
```

to a path that doesn't exist (case change is the most realistic regression):

```json
"./adapters/gam": {
  "import": "./dist/adapters/Gam.js",
  "types": "./dist/adapters/gam.d.ts"
},
```

Save the file. **Do not stage or commit.**

- [ ] **Step 3: Run the build, expect failure**

Run:

```bash
bun run build
```

Expected:
- `build:js` and `build:types` succeed (they read `tsconfig.json` and source, not `exports`).
- `check:exports` fails. attw reports a resolution failure (rule like `no-resolution`) for the `./adapters/gam` entry, citing the bogus `Gam.js` path.
- Overall exit code is non-zero.

If the build succeeds despite the corruption, the check is not actually wired correctly — return to Task 4 and debug.

- [ ] **Step 4: Revert the corruption**

```bash
git checkout -- package.json
```

Verify with `git diff package.json` — output should be empty.

- [ ] **Step 5: Build again to confirm the revert restored a passing state**

```bash
bun run build
```

Expected: exit 0. (Symmetric to step 1.)

No commit in this task — it's a verification probe.

## Appendix: rollback notes

If the integration causes problems on `main` after merge:

1. Revert the merge commit (creates a clean reverse-diff).
2. The previous CI YAML step is restored as part of the revert; no manual restoration needed.
3. Both devDeps stay in `bun.lockb` until a separate `bun remove` cleans them up — harmless but worth doing.

If only `check:exports` needs to be temporarily disabled (e.g. CLI bug discovered upstream):

1. Edit `package.json` to remove `&& bun run check:exports` from the `build` script.
2. Open a follow-up issue tracking the upstream problem.
3. Do not delete the `check:exports` script itself or the devDeps — restore the chain when the upstream issue is resolved.
